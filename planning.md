# Zedville — Refactor & Fix Planning (Controllers / Services / Providers / Kernel)

Sequenced by risk/impact. Each phase is independently shippable — don't start phase N+1 until phase N is merged and verified, since later phases assume earlier fixes are in place. No functionality should change as a *side effect* of refactors in Phase 2-4; only Phase 1 changes behavior (it's bug fixes).

## Phase 1 — Critical/High bug fixes (behavior-changing, ship individually, each with a test)

Do these one at a time, each as its own PR, each verified against a real login → salary → bill-deduction flow before merge.

1. **Fix the ledger split** (`bugs.md` #1): point `BankController::creditMonthlySalary()` at `Transaction1` instead of `Transaction`, matching the column shape used everywhere else (`transaction_date`, `type`, `category`, `amount`, `balance`, `bank_account_id`, `sid`). Verify: credit salary, confirm it appears in the same balance chain `ensureMonthlyBills` reads from, confirm bills deduct correctly afterward.
2. **Add missing imports** (`bugs.md` #3, #4): `use App\Models\Mailbox;` in `CitizenActivationController.php`; `use App\Helpers\MailboxScheduler;` in `AdminStudentController.php`. Trivial, but verify the code paths that call them actually execute without error afterward (write a quick feature test hitting `authorize_direct_deposit` and `add_student`).
3. **Move salary/bills off login-trigger onto a real schedule** (`bugs.md` #2): create an Artisan command (e.g. `students:process-monthly-finances`) that chunks over active students and calls `StatementGenerator::generateForUser()` / the bill-posting logic on the correct day-of-month, idempotently (reuse the existing "already processed this month" guards). Schedule it in `Console/Kernel.php` with `->dailyAt(...)` (checking day-of-month inside the command) rather than depending on user login. Keep the login-triggered call as a redundant safety net during transition, remove once the scheduled job is proven reliable for 1-2 full months in production.
4. **Fix badge scheduling** (`bugs.md` #7): change `monthlyOn(31, ...)` to `lastDayOfMonth(...)`.
5. **Wrap balance mutations in transactions with row locks** (`bugs.md` #5): standardize on a small helper — e.g. `BalanceService::withLockedBalance($userId, callable $fn)` that opens `DB::transaction()`, does `Transaction1::where('user_id',$userId)->latest('id')->lockForUpdate()->first()`, and hands the balance to the callback. Migrate `EFDController::storeDonation`, `OrderController::placeOrder`, `ProfileController::storesurvey` onto it one at a time, each with a concurrency-oriented test (two rapid requests, assert no overdraft).
6. **Resolve admin middleware gap** (`bugs.md` #6) — once Phase 0 step 2 confirms the gap is real, add `admin` middleware to the `RouteServiceProvider` admin group (or per-route in `admin.php`, whichever the existing pattern favors). Treat as security-priority, don't wait for the rest of Phase 1.
7. **Decide and resolve the dead penalty trigger** (`bugs.md` #9) — get a product decision (enable or delete), implement accordingly.

## Phase 2 — Structural extraction (no behavior change, pure refactor, needs regression coverage first)

Before starting Phase 2, get baseline test coverage (feature tests) around: login flow, salary credit, bill posting, order placement, donation, survey submission. Refactors below must not change observable behavior — verify via these tests before/after each step.

1. **Extract a `LedgerService`** wrapping the "get latest `Transaction1` balance" pattern — IN PROGRESS, started 2026-10-10. The actual count turned out to be 80+ call sites, not ~13 (`app/Services/LedgerService.php`, built on the existing `BalanceService::lockedBalance()`). Migrated so far: `BankController::ensureMonthlyBills()` and `banks_penalty()` (both had a `max(0, ...)` floor-at-zero rule, preserved via a `floor_at_zero` option on `LedgerService::post()`), verified against `tests/Feature/Bank/ScheduledFinanceSidTest.php`. Also migrated: `EFDController::storeDonation()`, `OrderController::placeOrder()`, `BankController::processBillPayment()`/`emengercyfundaccount()`, and the "Primary Savings Account"/"primary" paths of `processTransfer()` (its emergency-fund/money-market paths update `bank_accounts` fields directly, never touch `transactions1`, so there was nothing to migrate there). Each was a pure code-consolidation move once checked for quirks (floor-at-zero preserved via `LedgerService::post()`'s `floor_at_zero` option where it existed; `placeOrder`'s per-item negative-balance guard kept as an explicit arithmetic check). Deliberately NOT migrated: `creditMonthlySalary()` - its balance lookup orders by `transaction_date` (not `id`) because the salary transaction is backdated to the 6th, which `LedgerService` doesn't support and migrating would silently change. Also found and deleted along the way: `processAutoDebits()` (dead, unreachable, used the wrong `Transaction` model) and fixed `store_auto_debit()` (used the wrong `Transaction` model for its balance check, so it always rejected - see bugs.md). Remaining in `BankController`: mostly read-only/display methods and a few that don't touch `transactions1` at all (beneficiary/auto-debit-request/direct-deposit storage, PIN update) - the Phase 2 #1 extraction is effectively done for this controller's actual ledger-writing call sites. `OrderController`/`EFDController` have a few more spending-tracker-adjacent call sites outside what this pass covered.
2. ~~Extract fixed-bill posting into one method~~ — RESOLVED differently, 2026-10-11: `AuthenticatedSessionController::ensureMonthlyBills()` turned out to be dead code - its only call site was inside a commented-out block (`/*if ($isEligible && $now->day >= 7) { $this->ensureMonthlyBills($user); }*/`), same pattern as the Civic Chamber "duplication" that was actually dead code too (Phase 2 #5). Deleted the whole method plus the now-unreachable `$isEligible`/`$now`/`$accountCreatedAt` computation and 4 unused imports (`RouteServiceProvider`, `BankAccountController`, `MailboxHelper`, `MailboxScheduler`) found alongside. What remains - `CitizenActivationController`/`CitizenActivationService`'s two real copies of the fixed-bill loop, plus `BankController::ensureMonthlyBills()` (already migrated to `LedgerService`) - is genuine duplication across the one-time "new citizen" provisioning path vs. the recurring monthly path, which have different enough context (no existing-row check needed on first provisioning, different date anchoring) that consolidating them is a smaller, lower-priority win than this item implied - not attempted here.
3. **Add a `SetSelectedSchool` middleware** (or a global model scope) to replace the ~40+ manual `session('selected_school')` reads scattered through `AdminEducationController` and siblings - PARTIALLY MOOT, checked 2026-10-11. The correctness-critical half of this item is already done: `IsAdmin` middleware already pins `session('selected_school')` to the acting user's own school on every request for non-super-admins, so the session value itself was never the actual gap. What's left - ~40+ individual controller methods calling `session('selected_school')` directly instead of through one shared accessor - is purely cosmetic repetition, not a bug, and a mechanical find-replace across 16 files for style alone isn't worth the transcription risk. Also found and deleted: `App\Models\BaseModel` and `App\Models\Traits\HasSidScope` - two separate, duplicate implementations of a global Eloquent scope that would have done exactly this automatically, except neither was ever actually used by a single model anywhere in the codebase. Dead, unused infrastructure - deleted rather than wired up, since retrofitting 16 controllers' models onto an automatic scope now would be a real behavior-risk refactor (silently changing which rows a query returns), not a safe one.
4. ~~**Fix `sid` provenance** (`bugs.md` #14)~~ — DONE 2026-10-08 for the three call sites actually reachable from a non-session (console/scheduled) context: `creditMonthlySalary`, `ensureMonthlyBills`, `banks_penalty` in `BankController`. Verified with a real baseline test (`tests/Feature/Bank/ScheduledFinanceSidTest.php`) that reproduces the bug against the old code and passes against the fix. The remaining `session()->get('sid')` call sites are all on interactive student-initiated paths and were left alone - not touched, since the session value is correct there and `LedgerService` doesn't exist yet to make that a one-line change.
5. ~~**Consolidate Civic Chamber** (`bugs.md` #10)~~ — DONE differently 2026-10-07: the admin controller's student-facing copy was dead/unrouted, not actually drifting from EFDController's — deleted it instead of building a shared service. No consolidation needed since there was only ever one live implementation.
6. **Introduce Laravel policies** for the admin/tutor/student checks currently duplicated ad hoc - PARTIALLY DONE differently. Surveyed every remaining ad-hoc `$user->role ==`/`in_array($user->role, ...)` check codebase-wide (`ClosetController`, `AdminDashboardController`, `AuthenticatedSessionController`, `EFDController`). Found and fixed a second instance of the exact bug class `ClosetController::requireAdmin()` had: `AdminDashboardController::toggleViewMode()` re-derived the admin/tutor role list locally instead of calling `User::isAdminOrTutor()`, missing role 0 - see `bugs.md`. The rest all check one specific role (super-admin-only, student-only, tutor-only), not a re-derived multi-role group, so they don't have the same risk and weren't touched. Formal Laravel Policy classes (tied to Eloquent models, `AuthServiceProvider::$policies`) were not introduced - these checks are generic role gates, not per-resource ownership checks, so `Gate::define()` or (what's already there) the `User::isX()` helper methods are the better-fitting primitive; building Policy classes for a fit they don't match would be architecture for its own sake. The real, concrete value here (catching the missing-role-0 bugs) is done; the "introduce Policies" framing in the original item isn't the right tool for what's left.

## Ground rules for whoever executes this plan

- No PR should combine a bug fix with a refactor — reviewers need to tell "behavior change" from "same behavior, cleaner code" at a glance.
- Every Phase 1 item needs a test that would have caught the original bug, not just a manual smoke check.
- Do not touch DB schema/migrations as part of any Phase 1-3 item unless explicitly called out (only the column-rename item in Phase 4 touches schema, and it's flagged as needing special care).
- Re-run the verification steps in Phase 0 whenever revisiting this plan after a gap in time — the codebase may have moved since this audit.

See `bugs.md` for the full defect list this plan resolves, and `ProjectArchitecture.md` for system context.
