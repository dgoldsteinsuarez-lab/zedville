## Phase 3 — Larger consolidations (bigger risk, plan as dedicated initiatives, not incidental to other work)

1. ~~Evaluate the two badge systems~~ (`bugs.md` #11) — DONE 2026-10-12. ## Phase 6 — FinHero global point defaults (2026-10-18, driven by `Zedville_FinHero_Point_Values_v1.pdf` + direct product instruction)

Comparing the FinHero Point Values doc against the live scoring code found a much bigger gap than expected: the doc's tiered "Approach System" (3/2/1/0 points by attempt tier, with hints) barely exists. Task 1 has a tier array but with different numbers (`[1,0,0,0]` pts over `[1,2,2,∞]` attempts, not the doc's `[3,2,1,0]` over `[2,2,2,∞]`); Tasks 2-4 are flat "1 point, first try only, no tiers"; Task 5 doesn't exist as a view. Live max-points per task (1/8/10/8) don't match the doc's table (3/24/33/24/3) anywhere. Given the size of that gap, the user chose to sequence it: global point-defaults admin screen first (this phase), the actual Approach System/point-value rebuild in the task views later (not started).

1. ~~Global default point value per activity, editable in Admin, applying to every school~~ — DONE 2026-10-18. New `finhero_activity_defaults` table (one row per `activity_key`, seeded from whatever distinct keys already existed live - the real dev DB's `finhero_activity_registry` was empty, so nothing to seed in practice yet). `finhero_activity_registry.max_points`/`salary` were already nullable; relaxed `addActivity`'s validation so leaving them blank is accepted (previously `required_if:type,task`) rather than forcing every assignment to repeat the same number. Resolution is "row's own value overrides the default; null falls back to it," wired into every place that reads points for real (`FinheroBadgeCalculatorService::getTotalAvailable()`/`getActivityPoints()` via a `LEFT JOIN ... COALESCE`, and `FinheroStudentController::awardPoints()`/`savePoints()` via a direct fallback lookup) - not just the admin display, so editing a default has real effect. New Super-Admin-only screen at `admin/finhero/point-defaults` (platform-wide setting, not a single-school one) to view/edit existing defaults and register a default for a not-yet-existing `activity_key`. Tested via `tests/Feature/Admin/FinheroPointDefaultsTest.php` (access control, default-change propagates to non-overridden rows, explicit row override is untouched by default changes, award endpoint falls back correctly).
2. ~~Task 1~~ — DONE 2026-10-18, first of the task-by-task Approach System rebuild. New `App\Services\FinheroApproachSystem` (the doc's §2 tier table: `[3,2,1,0]` points over `[2,2,2,∞]` wrong attempts) is the single source of truth both the frontend tier-tracking and the backend point-resolution agree on - the client only ever reports which tier it's on, never a raw point number, same trust principle `awardPoints()` already used for `source_key`. `task-1.blade.php`'s `APPROACHES` array and all its point-display text now match the doc exactly (previously `[1,0,0,0]` over `[1,2,2,∞]`).

   Found and fixed a real, pre-existing, live bug while wiring the save call through: `FinheroStudentController::savePoints()` validated the per-question `source_key` ("task_1_question_1") directly against `finhero_activity_registry.activity_key`, which only ever has rows for the whole task ("task_1") - every save call from any task view would 422. `finhero_student_points` had zero rows in the live dev DB, consistent with this never having worked for any task. Fixed by deriving the base `activity_key` (stripping the `_question_N` suffix) for the registry/active-task check, while still tracking per-question earned-points bookkeeping by the full compound key - this incidentally also unblocks Tasks 2-4's existing flat per-question saves, not just Task 1's new tiered ones.

   `finhero_activity_defaults` seeded with the doc's §3 table for all five tasks (`task_1`=3 through `task_5`=33/24/3 as applicable) via a new migration - task_5's default is ready even though its view doesn't exist yet (see `ProjectArchitecture.md` §14.4). Tested via `tests/Feature/Finhero/Task1ApproachSystemTest.php` (tier→points resolution, duplicate-scoring prevention, inactive-task rejection, the validation-bug fix itself).

   **Still open:** Tasks 2-4's scoring (currently flat "1pt, first try only, no tiers" - same shape `Task1ApproachSystemTest` now proves wrong for Task 1) and Task 5 (doesn't exist in this repo - see `ProjectArchitecture.md` §14.4, pending Daniel sharing whatever's on Hostinger). Also: no school currently has an actual `finhero_activity_registry` row for `task_1` (the table is empty in the live dev DB) - the Approach System now works correctly once a Super Admin registers/activates Task 1 for a school via the Activity Manager, but that registration step itself hasn't been done for any real school yet.

## Ground rules for whoever executes this plan

- No PR should combine a bug fix with a refactor — reviewers need to tell "behavior change" from "same behavior, cleaner code" at a glance.
- Every Phase 1 item needs a test that would have caught the original bug, not just a manual smoke check.
- Do not touch DB schema/migrations as part of any Phase 1-3 item unless explicitly called out (only the column-rename item in Phase 4 touches schema, and it's flagged as needing special care).
- Re-run the verification steps in Phase 0 whenever revisiting this plan after a gap in time — the codebase may have moved since this audit.

See `bugs.md` for the full defect list this plan resolves, and `ProjectArchitecture.md` for system context.
