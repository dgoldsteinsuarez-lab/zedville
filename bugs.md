### Fixed 2026-10-10 - User::avatar() self-referential relation
`User::avatar()` was defined as a `belongsTo` relation with the SAME name as the underlying `avatar` column it reads as its own foreign key - self-referential. Whenever a `User` instance's attributes array didn't already contain an `avatar` key (any model not loaded via a full `SELECT *`, e.g. `User::factory()->create([...])` without explicitly setting `avatar`, or a freshly-registered instance before a refresh), accessing `$user->avatar` fell through to relation resolution instead of the plain column value, and that resolution itself tried to read `$user->avatar` to find the FK value - throwing `Undefined property: $avatar`. This was the root cause of the stock `ProfileTest::test_profile_page_is_displayed` failure (not actually a Breeze-scaffolding mismatch as first assumed). `avatarRelation()` already existed as the correctly-separated relation accessor and is what `AdminStudentController`/`details.blade.php` actually use for object-style access (`$student->avatarRelation->name`) - every other call site in the app (`ProfileController`, `profile-sidebar.blade.php`, etc.) already treats `$user->avatar` as the plain scalar id, so the colliding `avatar()` method served no purpose. Deleted it. Covered by `tests/Feature/UserAvatarAttributeTest.php`.

Still open (not fixed, lower priority since PHP's numeric-string coercion mostly papers over it): `bank_accounts.sid` is `varchar(50)` live vs `bigint` in migrations (same drift as `users.sid`), and the three `*_amount` columns are `varchar(255)` live vs `decimal(12,2)` in migrations.
- FIXED (dead code, not a live bug): `BankController::processAutoDebits()` was a `protected` method with zero call sites anywhere - never invoked by any route, command, or job. Deleted rather than fixed, since nothing calls it. Also removed a dead commented-out draft of `bank_statement_show()` found alongside it.
- FIXED (critical, previously undiscovered): `BankController::store_auto_debit()` checked balance against the legacy `Transaction` model (table `transactions`), not `Transaction1`/`transactions1` (the one every other balance check in the app uses, and the only one any real money ever gets written to - `transactions` has 0 rows in the live dev database). Six real forms post here (electricity/internet/school/water auto-debit, the generic auto-debit authorization form, and the citizen-activation onboarding flow), so this was a live, user-facing dead end. - FIXED (critical, previously undiscovered): `app/Jobs/ProcessScheduledBillPayment.php` had **no `namespace App\Jobs;` declaration** - the class actually lived in the global namespace, but `BankController` imports and dispatches it as `App\Jobs\ProcessScheduledBillPayment`. Any "schedule" or "recurring" bill payment (`store_pay_bill` with `type != 'now'`) would fatal with a class-not-found/already-declared error the moment it ran - this code path looks untested/never exercised in practice. The job also carried its own divergent copy of `processBillPayment()`'s logic (missing `sid`, the row lock, and the floor-at-zero rule) instead of calling it. Fixed the namespace and had the job delegate to the real controller method, matching the pattern `ProcessScheduledTransfer` (the sibling job for money transfers) already used correctly. `processBillPayment()` itself also had the same `session('sid')`-in-console-context bug as the scheduled finance jobs; fixed and migrated onto `LedgerService`. Covered by `tests/Feature/Bank/ScheduledBillPaymentTest.php`.

### Added/fixed 2026-10-08
- FIXED (re-discovered as live, not just theoretical): `sid` provenance (`planning.md` Phase 2 #4). `BankController::creditMonthlySalary()`, `ensureMonthlyBills()`, and `banks_penalty()` wrote `'sid' => session()->get('sid')` into every ledger row. All three are called directly from `Console\Kernel`'s scheduled finance job (and `ApplyMonthlyPenalty`/`AuthenticatedSessionController` for the penalty case) for arbitrary other students, with no HTTP session in play - every scheduled run was silently stamping NULL `sid` on every student's salary, bill, and penalty transactions. Fixed by using `$account->sid`/`$user->sid` directly instead of the session. Covered by `tests/Feature/Bank/ScheduledFinanceSidTest.php`, which reproduces the bug (fails against the old code) and passes against the fix. The other ~18 `session()->get('sid')` call sites in `BankController`/`OrderController` are all on interactive, self-service paths (transfer, survey, order, auto-debit) reached only from the acting student's own session, so they were not affected - not touched in this pass.
- FOUND (separate, not yet fixed): schema drift on `users.sid` - migrations define it as `unsignedBigInteger` (`2026_09_30_131000_add_missing_columns_to_users_table.php`), but the live dev database (imported from a SQL dump, not purely migrated) has it as `varchar(50)`. A fresh `migrate` from this repo's migrations alone would NOT reproduce the live schema for this column. Needs a migration that documents/aligns the real column type - flagging rather than fixing blind, since changing a column type touching every `users.sid` read/write needs its own careful pass. Same drift also confirmed (2026-10-11, while testing `SupermarketProductController`) on `supermarkets.sid` (bigint in migrations, varchar live) and noted earlier on `bank_accounts.sid`/`*_amount` columns - all still open, none fixed yet.
- FIXED: 31 tables (`products`, `orders`, `order_items`, `donations`, `finhero_*`, `activities`, `npos`, `stores`, `student_closet`, etc.) existed in the live dev database with **no migration at all** - discovered while trying to write a feature test for order placement, which needs `products`/`orders`/`order_items`. `migrate:fresh` (what `RefreshDatabase`-based tests run) could not reproduce the real schema, and this is also a disaster-recovery gap (migrations alone couldn't rebuild the database from scratch). Added `database/migrations/2026_10_10_000001_create_missing_live_schema_tables.php`, which creates all 31 tables from `SHOW CREATE TABLE` output captured against the live dev database (verbatim, not hand-translated), guarded by `Schema::hasTable()` so it's a no-op against a database that already has them. Verified byte-for-byte identical `SHOW CREATE TABLE` output between the dev DB and a fresh `migrate:fresh` test DB for several of these tables, and confirmed the two databases' table lists now match exactly.

### Found, NOT fixed (noted for a future pass) - 2026-10-11
`Admin\LowBudgetActivityController::lba_position()` (formerly `AdminEducationController::lba_position()`) is structurally broken compared to its three siblings (Mba/EmergencyFund/HighBudgetActivity PositionController). It reads `session('sid')` instead of `'selected_school'` (every sibling and the `IsAdmin` middleware use `'selected_school'` - `'sid'` is never actually set to anything by this app, so the resulting `$sid` is always `null`), has no `cid` (class) scoping at all, and does `updateOrInsert(['user_id' => $userId, 'id' => 4], [...])` - treating the `mba_position` table's auto-increment primary key as if `id` 4 were a fixed "slot" reserved for Low Budget Activity, rather than matching on `activity_key`/`cid` like the siblings do. In practice this only works by coincidence on an otherwise-empty table (the first call inserts id=4 successfully); once row id 4 is taken by anything else, the insert would fail outright. Preserved verbatim during the `AdminEducationController` -> `LowBudgetActivityController` extraction rather than silently "fixed" into different behavior - needs its own dedicated redesign to match the per-class pattern its siblings already use, which is a real feature change, not a refactor.
