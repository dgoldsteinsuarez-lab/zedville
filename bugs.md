## 🟠 High

### 19. Consumer profile survey is mathematically impossible to complete — blocks all new student activation
Found 2026-10-18 while trying to open a test student account; root cause fully traced 2026-10-18 (initial diagnosis below was wrong on one point - corrected).

`CitizenActivationService::getNextRoute()` Step 4 gates onboarding on `ConsumerSurvey::where('user_id', $user->id)->exists()`. The step's view includes `citizen-activation.layouts.surveys`, whose interactive logic lives in `public/asset/front/js/surveys.js` (loaded globally via `layouts.profile`) - **this part does genuinely submit for real**: `showResults()` POSTs to `/profile/storesurvey` (the same already-working, already-tested `ConsumerSurveyController::storesurvey()` used for the monthly redo). My first pass missed this file entirely and wrongly concluded the quiz never submits at all - corrected here.

The actual blocker is earlier in the flow: the grocery-selection step's "Continue" button is hard-disabled until exactly 11 checkboxes are checked (`updateGrocerySelection()`: `nextBtn.disabled = (totalCount !== 11)` - 10 student-picked items + 1 auto-included "cooking oil"). The checkbox list is populated from `GET /api/groceries/{diet}`, which filters `supermarkets.type` against exactly `omnivore`/`vegetarian`/`pescatarian`/`vegan`. The live dev DB's `supermarkets` table has 3 rows total (Bread, Milk, Eggs), all tagged `type = 'groceries'` - none match any diet, for any student, ever. The list always renders empty, so 11 checked items can never be reached, so the button can never enable, so the survey can never be submitted - not a code bug exactly, but a genuine, total content gap: the grocery catalog needed for this to work doesn't exist.

Worse: there was no way to even start fixing this via the admin panel. `supermarkets.type` is meant to reference a `Supermarketname` row's `name` (the admin product form's "type" dropdown lists `Supermarketname::all()`), but **nothing in the entire app ever created a `Supermarketname` row** - `SupermarketProductController`/`PenaltyWantsItemController` only ever read from it. The table was empty with zero path to populate it.

**Fixed 2026-10-18:** added the missing admin CRUD for store names (`SupermarketProductController::storeNamesIndex/Store/Delete`, new screen "Supermarket Stores" in the nav, separate from the existing "Supermarket Products" screen). An admin can now create a store (e.g. named "Omnivore") and then assign products to it via the existing, already-working Supermarket Products screen. Tested via `tests/Feature/Admin/SupermarketStoreNamesTest.php` (store creation, a diet-tagged product actually appearing via `/api/groceries/{diet}`, store removal).

**Catalog seeded 2026-10-18** from Daniel's real pricing doc (`Salary and Savings Computation.xlsx`): 21 real, priced items per diet (20 selectable + a literal "Cooking Oil" entry, auto-included by the survey's own JS) via a new migration (`2026_10_18_000005_seed_supermarket_diet_catalog`). Also widened `supermarkets.quantity` from `int` to `decimal(10,2)` (a prerequisite fix - the doc's real quantities are fractional, e.g. 0.8kg, 3.5kg; the old integer column would have silently rounded them, throwing off the price×quantity totals the survey computes client-side). Each row's `(unit_price, quantity)` was verified to multiply to the doc's own stated monthly cost for that item while transcribing. Note: the doc's separate basket-total summary figures (130.00/158.851/115.614/165.197) do **not** equal the sum of all rows for any diet - that total appears to reflect a different, smaller selection, not the full catalog; not reconciled, since the per-item prices (not that aggregate) are what the survey and catalog actually need. Tested via `tests/Feature/ConsumerSurveyGroceryCatalogTest.php` (≥11 items incl. cooking oil per diet, fractional quantities preserved).

The consumer-profile survey should now be genuinely completable by a student, not just skippable - **not yet manually verified end-to-end in a browser**, only via the API-level tests above (grocery list population, item counts). The "Wants" category items from the same doc (movie tickets, games, etc.) and the two linked Google Docs (bank-statement tagging detail, interest-rate reference) were not used this pass - out of scope for just unblocking the survey.

**Temporary unblock (kept as a fallback, no longer strictly required for new activations once the catalog above is confirmed working end-to-end):** `CitizenActivationController::skipConsumerProfile()` + a "Skip for now" button create a zero-cost placeholder `ConsumerSurvey` row. Tested via `tests/Feature/CitizenActivation/SkipConsumerProfileTest.php`.

### Fixed 2026-10-10 - User::avatar() self-referential relation
`User::avatar()` was defined as a `belongsTo` relation with the SAME name as the underlying `avatar` column it reads as its own foreign key - self-referential. Whenever a `User` instance's attributes array didn't already contain an `avatar` key (any model not loaded via a full `SELECT *`, e.g. `User::factory()->create([...])` without explicitly setting `avatar`, or a freshly-registered instance before a refresh), accessing `$user->avatar` fell through to relation resolution instead of the plain column value, and that resolution itself tried to read `$user->avatar` to find the FK value - throwing `Undefined property: $avatar`. This was the root cause of the stock `ProfileTest::test_profile_page_is_displayed` failure (not actually a Breeze-scaffolding mismatch as first assumed). `avatarRelation()` already existed as the correctly-separated relation accessor and is what `AdminStudentController`/`details.blade.php` actually use for object-style access (`$student->avatarRelation->name`) - every other call site in the app (`ProfileController`, `profile-sidebar.blade.php`, etc.) already treats `$user->avatar` as the plain scalar id, so the colliding `avatar()` method served no purpose. Deleted it. Covered by `tests/Feature/UserAvatarAttributeTest.php`.

Tested via `tests/Feature/Admin/ImpersonationReadOnlyTest.php` (a write is blocked while impersonating, a read still works, returning to your own account still works, writes are unaffected outside impersonation) - running the full suite afterward caught that the new middleware ran ahead of `ImpersonateController::start()`'s own stacking guard and changed its 403 into a 302; fixed via the `admin.impersonate.start` exemption above rather than leaving the more specific guard shadowed.
